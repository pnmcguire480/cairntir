The remaining Windows assertion failure rejected an ordinary completed artifact rewrite as `UNSAFE_SOURCE`, before reaching the expected `ATTACHMENT_CONFLICT`. On native Windows Python 3.12, path and descriptor stat calls returned different `ctime` values for the same file, while their birth times and device/inode/size/mtime matched. This agrees with the [CPython report](https://github.com/python/cpython/issues/157671) and [Python 3.12 timestamp documentation](https://docs.python.org/3.12/whatsnew/3.12.html).

The bounded reader repair uses birth time for cross-API identity where available, preserving the existing ctime fallback elsewhere. Separate path-to-path and descriptor-to-descriptor change-clock checks remain, alongside file identity, bounds, length and link/reparse protections. Fourteen independently authored controls were frozen before the repair: the unchanged baseline produced **one failure and 14 passes** including the original conflict case. The candidate passes **25 cases**, including the complete existing attachment suite. Removing only the descriptor change-clock check from an isolated in-memory copy causes the independent same-size/restored-mtime control to fail. The original failure remains retained.

An actual isolated Windows Python 3.12.14 run also reproduced the old reader refusal, read the revised bytes with the candidate, and obtained `ATTACHMENT_CONFLICT` through the real attachment store. Original attachment bytes and parent isolation remained intact. Independent source review found no blocker in this repair. These are stat-based checks, not a universal race-proof snapshot: birth time is identity, and same-size/restored-mtime changes before the first descriptor observation have a detection limit. Fresh hosted results remain required.
