# R08 public plugin submission and acknowledgement matrix v1

Frozen independently before plugin implementation. The harness drives registered commands and mocked Obsidian controls, filesystem and execFile callbacks. It never calls private plugin methods. This is public boundary acceptance, not native Obsidian or installed-backend proof; a real process pilot remains required.

Forms expose a question/resolution text area, an opening room, an optional owner, and evidence selection recognizable by its field label. The minimal desktop form may accept visible memory IDs separated by commas; it must resolve these against a validated same-wing workspace manifest to submit exact immutable UUID/hash references. The matrix uses visible IDs 7 and 8. User text and owner are preserved exactly; an empty owner becomes null. Open questions may omit evidence; resolutions require at least one selected supporting memory. Selecting arbitrary unknown, duplicate, wrong-wing or hash-invalid evidence must not produce a queued request. This harness does not impose plugin method names or internal state layout.

Startup, note events, opening and cancelling a form do not write requests or launch sync. Explicit submission produces one retained UUID-named core-schema JSON request and invokes the configured Python/store/wing using execFile, no shell, hidden window and bounded output/time. The original notes and manifests are not rewritten by submission. Recheck configuration and selected question/evidence bindings before queuing; a stale, wrong-wing or malformed register/workspace must be surfaced without mutation. A failed queue write must not launch a process or claim storage; a corrected retry can queue once.

Accept a saved acknowledgement only from exactly one matching per-file result with a committed question-receipt.v1 receipt. Match request UUID and operation, validate positive nonboolean IDs, canonical UUIDs, lowercase hashes and boolean replayed. Opening acknowledgement must match the submitted question content hash. Resolution acknowledgement must match the selected question UUID, local drawer ID and original hash, and name a positive resolution drawer ID. Missing, duplicate, wrong-file, wrong-operation, changed question binding and malformed receipts remain unconfirmed. A malformed/wrong-wing report is not a receipt. An ordinary numerical exit 1 may carry an authentic partial-success report; a killed/signalled/spawn-failed process or other exit does not become successful because stdout resembles a receipt.

After an uncertain/rejected response, explicit retry from the same form retains the exact queued request and UUID; no second proposal or payload rewrite. A committed receipt plus acknowledgement-write or projection failure must truthfully say stored while disclosing the failure/retry need and retaining the request. Unrelated rejected requests in an exit-1 report must not erase the matching committed result. Error notices must not falsely claim saved/committed, while real acknowledged success must be visible.

The matrix covers both opening and resolving, owner/evidence serialization, idle/cancel, valid acknowledgement, wrong report/receipt variants, process exit variants, partial saves, stale selection/configuration, invalid evidence, retry identity and queue failure. A future change to the UI harness requires a separately versioned repair explanation; these frozen originals remain intact. The earlier command-only harness is also retained. Product implementation may begin after this freeze; at most two repair rounds apply.
