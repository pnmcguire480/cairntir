# R08 public core question lifecycle contract v1

Independent public acceptance, prepared before implementation. No private custody claim. Original-directory artifacts only; no production installation/store or repository edits are authorized by this packet. One implementation round and at most two repairs; reserve verification effort.

## Public Python seam

`cairntir.questions` exports typed `QuestionError` and functions `open_question(store, request, *, wing)`, `resolve_question(store, request, *, wing)`, and `list_questions(store, *, wing, include_resolved=False)`. Use existing DrawerStore, portable source identities, transactions and execute_once; no new dependency or database schema.

Open request has exactly `schema: cairntir.question-open.v1`, canonical UUID `request_id`, `wing`, `room`, exact nonblank UTF-8 `content`, `owner` (nonblank string or null for unassigned), and `evidence` (possibly empty list). Evidence refs have exactly positive nonboolean `drawer_id`, canonical UUID `source_identity`, and lowercase SHA256 `content_sha256`. References must identify existing accessible nonsecret evidence in the selected wing, matching original bytes and immutable portable identity. An owner label is declared responsibility, not authenticated human identity.

Resolve request has exactly `schema: cairntir.question-resolve.v1`, canonical UUID `request_id`, `wing`, canonical UUID `question_id`, positive nonboolean `question_drawer_id`, lowercase SHA256 `question_sha256`, exact nonblank UTF-8 resolution `content`, and a nonempty `evidence` list with the same reference shape. The question binding must match its opening drawer's immutable portable identity, local ID and original text hash. Same-wing evidence linkage is validated; its prose is not automatically proved to establish the answer. Resolution is explicitly declared and evidence-linked.

Both successful operations return schema `cairntir.question-receipt.v1`, `operation` open/resolve, `status: committed`, `request_id`, stable `question_id` (the opening drawer's portable identity), `question_drawer_id`, `question_sha256`, `resolution_drawer_id` (null for open), and boolean `replayed`. Exact retries survive store close/reopen and return the original identities without another append, including retry after resolution. The same request UUID with altered payload or another operation conflicts. A new resolution request against an already resolved question is stale. Wrong wing/store/source identity/hash are rejected. Errors are surfaced as QuestionError; failed writes must not leave a partial resolution or change original evidence.

Opening and resolution are append-only drawers. Preserve original content, metadata, provenance and access state. A resolution inherits the opening question's room/layer and sensitivity/visibility, records untrusted provenance for filesystem/CLI-declared content, and links to the opening drawer. Dedicated structured question records are not editable via generic Obsidian correction. No prose parsing or ordinary supersedes edge closes a new typed question. A resolution-looking metadata object alone is insufficient: closure must bind to a committed dedicated workflow receipt naming that question and resolution drawer/hash, or equivalent existing durable registry proof. This prevents arbitrary metadata through ordinary remember from forging lifecycle completion.

## Register and legacy compatibility

`list_questions` returns schema `cairntir.question-register.v1`, `wing`, and `questions`. Each entry includes `question_id`, `drawer_id`, original `content`, `content_sha256`, `owner`, opening `evidence`, `status`, `legacy` boolean, and `resolution` (null unless validated; otherwise drawer_id/content/content_sha256/evidence). Default listing contains only open entries. With include_resolved true it also contains validated resolved entries and legacy history. Listing is read-only and survives restart.

Current untyped legacy `metadata.open_question` leaves remain visible as open, legacy, owner null; do not invent ownership from prose or arbitrary metadata. Preserve existing legacy handoff behavior: an ordinary historical superseder may remove such an untyped question from the current brief. Retain that original in register history as `legacy_superseded_unverified`, with resolution null; never relabel this as a new validated resolution. A dedicated resolve request may explicitly resolve a current legacy leaf using its actual UUID/ID/hash and valid evidence. Reject a resolution attempt against an already historically superseded legacy question. Newly typed questions require dedicated validated resolution regardless of ordinary superseders.

The eventual handoff and Obsidian register must share this lifecycle classification. Core tests freeze first; CLI, outbox acknowledgements, generated linked register and plugin commands receive a separate file/UI contract before their implementation. Keep 21 MCP tools; no additional MCP tool is required by this increment.

## Frozen core cases

Verbatim owner/evidence-bound open and restart replay; request UUID conflicts; evidence validation; supported append-only resolution with durable replay and stale rejection; wrong-store protection; ordinary superseder and forged-resolution metadata refusal; generic-correction refusal; legacy current/history distinction and explicit current-leaf resolution; failed-write rollback/retry. All fixtures use temporary synthetic stores. Original pre-existing handoff assertions remain valid. Critical wrong control: treating any supersedes edge as closure must be rejected.
