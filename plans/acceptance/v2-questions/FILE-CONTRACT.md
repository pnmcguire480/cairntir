# R08 explicit workspace, CLI and handoff contract v1

This adds to the unchanged core contract and precedes implementation of these surfaces. Public shared-workspace acceptance; no private evaluator claim. Reuse existing path confinement, generated-block preservation and explicit sync semantics.

`sync_workspace(store, *, vault, wing)` accepts the exact core question-open/resolve schemas from retained `cairntir-sync/outbox/*.json` alongside existing correction requests. No ordinary note is ingested. Keep `cairntir.obsidian-sync.v1` and its existing per-file result fields: committed/rejected status, core receipt, receipt_written and surfaced error. Store commitment and filesystem/projection success are distinct. Write acknowledged core receipts to `cairntir-sync/acknowledgements/<request_id>.json`. An acknowledgement failure leaves the committed receipt in the result and the request on disk; exact replay after restart repairs the acknowledgement without another drawer. Malformed or rejected requests do not prevent independent valid requests. Request UUID collisions with changed payload or another operation must not overwrite a valid acknowledgement with a false success.

Each successful refresh writes `cairntir-sync/questions.json` with the exact core register schema, wing and all visible question entries from include_resolved=True. Extra presentation fields such as relative note links are allowed. Generate `cairntir-sync/questions.md` with stable question UUIDs, explicit owner/unassigned state, current open versus declared-resolved versus unverified legacy history, and Obsidian wikilinks to opening drawers, supporting evidence and resolution drawers. All linked notes are present in the same wing-scoped memory projection. Preserve human annotations outside the owned block byte-for-byte; reject an unmarked pre-existing target. Escape reserved generated markers in Markdown without altering JSON evidence. Omit secret and other-wing questions/evidence; projection errors remain surfaced. No arbitrary note deletion or ingestion. Existing correction and generic memory views remain compatible.

CLI commands are `cairntir question open REQUEST.json --wing W`, `question resolve REQUEST.json --wing W`, and `question list --wing W [--include-resolved]`. Use the exact core request/receipt/register JSON. Successful stdout is one JSON value with no banners. Rejections produce nonzero exit and a visible diagnostic, never a committed-looking success. Read request files as strict UTF-8 JSON; reject duplicate keys. The command group must bypass unrelated host registration and update callbacks. Tests may inject a synthetic embedding provider through the existing CLI factory; this is entrypoint behavior evidence, not an installed real-model proof.

Actual `handoff.compose(store, wing=...)` must keep a new typed question in its open_questions section after an ordinary superseder or forged resolution metadata. It leaves that section only after a dedicated validated resolution. Restart preserves this distinction. Existing `_open_questions(list[Drawer])` legacy behavior remains valid for callers without durable validation context. Legacy current/history semantics remain exactly those in the core contract; handoff is not authorized to reopen all historical questions.

## Explicit Obsidian commands

Add command IDs `open-question`, `resolve-question`, and `show-question-register` to the existing plugin. Showing the register opens `cairntir-sync/questions.md`. Open/resolve show an explicit user-confirmed form; startup, opening a form and ordinary note edits must not queue mutations or launch sync. Opening collects exact question text, room, owner (unassigned allowed) and optional supporting-memory references. Resolution selects an open register entry, retains its UUID/local ID/hash binding, and collects explicit resolution text plus at least one selected valid evidence reference. Do not infer answers from edited prose or permit generic correction to resolve a structured question.

After explicit submission, preserve the queued request and its UUID across retry. Use the configured Python, store home and wing with shell:false and hidden subprocess window. Distinguish valid committed receipt, rejected/missing/mismatched receipt, acknowledgement-write failure and projection failure. A success message requires exact request binding: matching request UUID and operation; matching opening text hash for open; matching question UUID/local ID/hash for resolve. A bare exit code or a different question's receipt is not success. Partial filesystem success retains an honest saved-in-store/retry message and the request. Reject stale active selection/config changes before creating a new request. The Node public harness initially verifies command registration and lack of eager mutations; the complete submission/receipt matrix remains an explicit required plugin review/pilot, not inferred from that small harness.

## Executable scope

Freeze backend workspace roundtrip and links, retained acknowledgement failure/retry, per-file rejection isolation, annotation/unmarked target protection, CLI JSON/diagnostic/duplicate-key behavior and callback purity, durable handoff classification, and Node explicit command/no-eager-mutation checks. Original core tests and historical plugin/correction acceptance remain unchanged. Wrong control: ordinary supersession closes a typed question, or mismatched receipt is presented as saved, must fail the relevant acceptance/pilot.
