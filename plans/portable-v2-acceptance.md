# Portable evidence v2 acceptance contract

Independent author: `/root/foundation_review`. Implementer: `/root`.
Authorized continuation: request drawer #1262, following #1237.
This is a new acceptance generation. Original foundation artifacts remain
unchanged. Runtime implementation starts only after this contract and its
independent tests are frozen.

## Outcome and boundary

An operator can export an archive or an explicit selection, import it into
another local store, and relay it onward without changing original evidence,
misbinding numeric references, duplicating existing identities, or activating
foreign approval and execution history. Imports either commit their whole graph
or leave no partial evidence, vector, identity or successful workflow receipt.

The 25-case independent suite is `tests/unit/test_portable_v2_acceptance.py`.
The real schema-v6 SQLite fixture is `plans/portable-v2-v6.fixture`; fixture
provenance is recorded separately. Both are frozen inputs, not regenerated by
the implementation. Tests use isolated stores and deterministic local embeddings;
they make no semantic-model or commercial-host claim.

## Public API agreed before implementation

```python
portable.export_bundle(
    store, path, *, drawer_ids=None, wing=None, room=None, signing_key=None
) -> dict
portable.import_bundle(
    store, path, *, verify_key=None, idempotency_key=None
) -> dict
store.portable_identity(drawer_id) -> str
store.portable_source(drawer_id) -> dict
store.portable_relations(drawer_id) -> list[dict]
```

Export receipt fields are `count`, `complete: true`, and `bundle_hash`.
Import receipt fields are `count`, `imported`, `existing`, and `identity_map`
(canonical UUID string to destination integer drawer ID).
`count == imported + existing == len(identity_map)`.
Same-key replay may return the original counts, but must return the same map.
A reused key for a different canonical request is a typed conflict.

Without selection filters, export means the complete archive, including expired
history. The suite creates 100,003 actual records to exceed the former CLI cap.
An explicit selection includes required reference closure. Closure cannot escape
an explicit wing or room restriction; that request fails rather than silently
including a wider scope. Failure preserves any existing destination file and
leaves no partial export or temporary export file.

## Format and integrity

V2 is one UTF-8 JSON object:

```json
{
  "format_version": 2,
  "bundle_hash": "sha256:<hex>",
  "signature": null,
  "records": [
    {
      "identity": "<immutable drawer UUID>",
      "source_store_id": "<origin store UUID>",
      "source_drawer_id": 1,
      "drawer": {"content": "original text", "metadata": {}},
      "provenance": {},
      "references": [
        {
          "kind": "source",
          "path": "/content",
          "source_target_id": 2,
          "target_identity": "<target drawer UUID>"
        }
      ]
    }
  ]
}
```

`drawer` carries the original v1 drawer projection: wing, room, content, layer,
metadata, created_at, claim, predicted_outcome, observed_outcome, delta,
supersedes_id and belief_mass. It does not carry destination IDs or access state.
`provenance` is the complete original WriteProvenance dictionary.

The hashed payload is exactly `{"format_version": 2, "records": records}`,
with records sorted by identity. Canonical JSON uses sorted object keys, no
extra whitespace, UTF-8 without ASCII escaping, and finite JSON values.
`bundle_hash` is `sha256:` plus its SHA-256 hex digest. When present, signature
is `hmac-sha256:` plus HMAC-SHA256 of the same canonical payload. A reordered
record array therefore verifies against the same canonical payload. A requested
verification key rejects unsigned or incorrectly signed input.

Hashes bind identity, original content, provenance and relation mappings.
Malformed input, unsupported versions (including booleans), missing required
origin fields, conflicting duplicate identities and invalid mappings raise a
typed CairntirError. No caller-supplied local ID may attach a foreign record to
an unrelated destination record.

V2 deliberately preserves external URL text and source citations as inert
evidence. It never follows them. V1's URL prohibition, envelope shape and
reference rejection behavior stay unchanged.

## Stable originals and references

The drawer UUID is allocated once and survives restart, re-export, import,
re-layering, belief adjustment, access updates and local anchor enrichment.
Different records do not become one identity merely because their text or
integer IDs match. A cloned store preserves existing UUIDs but allocates
different UUIDs for new records created independently on either side.

`portable_source` returns the exact original record, including original
metadata, provenance and reference map. A -> B -> C interchange preserves that
record exactly. Changes to mutable local retrieval state never rewrite it or
manufacture a new historical revision. A UUID arriving with different original
evidence is a conflict; imports do not overwrite history to resolve it.

Reference paths use RFC6901 notation relative to the original drawer projection.
Supported kinds are `supersedes`, `evidence`, `counterexample` and `source`.
Map supersedes_id, evidence_drawer_ids, counterexample_drawer_ids, walkthrough_id,
derived_from, and nested evidence_ids/parent_drawer_id fields. Map numeric
`cairntir://drawer/N` references in text without rewriting the text. Ordinary
numeric values such as an attempt count remain ordinary values.

`source_target_id` belongs to the referring record's source namespace.
It can differ from the target's original source_drawer_id when B authors a new
reference to evidence imported from A. The explicit target UUID is the portable
identity; local integer pairs are not deduplication keys. Where both records
share the known source namespace, an inconsistent numeric-to-identity rebinding
must be rejected. Clone divergence can produce the same source integer pair
for distinct UUIDs; never collapse those identities.

Every required target must exist in the bundle or already be known by its
immutable identity in the destination. Missing targets and missing reference
maps reject the whole import. `portable_relations` returns the original typed
reference fields plus the resolved `target_drawer_id`. Imported local
supersedes_id is explicitly mapped, and two competing successors remain two
branches. Specialized source metadata is retained as evidence, not rewritten
into an executable local record.

## Atomicity, migration and trust

Import validation and deduplication are race-safe. Separate processes importing
the same request concurrently yield one graph and one committed workflow
receipt. Overlapping bundles, changed file order and alternate retry keys reuse
known UUIDs. Successful receipt, identity map, drawer writes and vector writes
share one atomic operation. The suite injects both an embedding failure and a
SQLite failure on the second drawer insertion, then retries the same key.
Failed-attempt workflow receipts may remain; partial evidence and committed
success receipts may not.

The migration fixture contains three linked v6 drawers, full original
provenance, non-default access and belief state, embeddings, and a committed
workflow receipt. Every pre-existing drawer/vector/workflow column and existing
store-metadata entry must survive migration unchanged. New identity/schema
records are permitted; regenerated content, re-attested provenance, or reindexing
the old vectors are not. Reopening preserves assigned identities. Migration must
retain the project's existing backup-first safeguards.

Every imported local receipt is UNTRUSTED, even when a valid HMAC verifies a
source SYSTEM receipt. Preserve source sensitivity and validity bounds; imported
visibility is private. Keep exact original provenance separately. In particular,
an expired secret remains an expired secret after interchange.

Imported Discovery promotions, hotfix authorization/hash-chain records and
approval/capability metadata do not become active local Discovery, Reason,
workflow or execution state. Imported content remains retrievable as historical
evidence. HMAC verifies shared-key possession, not personal identity or authority.
No generic rewriting of CodeGlass fingerprints or hotfix hash chains is allowed.

Identity/source/relation reads and export preserve every persisted source table,
including access state and workflow logs. Import is an explicit write.
